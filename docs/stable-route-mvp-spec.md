# 最稳路线 MVP 规格

## 1. 这版产品先解决什么

第一版不追求自动写完整部剧本。

它先解决三个更真实、也更稳定的痛点：

1. 一个故事从点子走到大纲时，容易散、空、失焦。
2. 一旦进入长篇写作，人物、时间线、伏笔和世界规则很容易崩。
3. 现有 AI 大多只会继续写，很少会像专业开发系统那样帮人看出问题并组织改稿。

因此，这一版的产品定位应该是：

- 一个以“故事圣经”为中心的编剧工作台
- 一个以“场景卡 + 规则检查”为核心的改稿助手
- 一个帮助人类编剧保住长程逻辑和人物一致性的系统

## 2. 默认产品假设

为了尽快推进，我先采用这组默认假设：

- 目标用户：个人编剧或 2 到 3 人的小开发团队
- 创作语言：中文优先
- 作品类型：电影长片和剧集 pilot 共用一套开发流程
- 产品角色：共创和评审工具，不是全自动代写工具
- 第一版重点：开发期，不是投稿排版期

如果后面你要改方向，这套规格仍然能保留 70% 以上。

## 3. 为什么这条路线最稳

从行业方法和研究结果看，稳定性高的原因主要有四个：

1. Truby 的方法和官方软件都强调从 premise、人物、结构、场景到 rewrite 的完整开发流，而不是先生成成稿。
2. McKee 的人物方法强调真正有价值的是人物在压力下的选择，这要求系统保存人物内部逻辑，而不只是吐文本。
3. ScreenSkills 对 script editor 和剧本开发训练的描述都指向同一个事实：剧本开发本身就是持续评审与修订，不是一次性产出。
4. 近期剧本 AI 研究普遍说明，长篇剧本直接生成最容易在人物一致性、逻辑一致性和冲突处理上失稳。

所以第一版最应该把“事实、关系、时间线、改稿反馈”先管住。

## 4. 第一版核心价值

用户进入系统后，最直接应该得到四件事：

1. 把模糊点子压成可继续写的故事骨架。
2. 用一个统一的故事圣经保存人物、关系、世界、时间线和伏笔。
3. 在场景层持续发现逻辑漏洞、人物偏移和中段疲软。
4. 把“改哪里”说清楚，而不只是“再来一版”。

## 5. MVP 工作流

### 步骤 1：创建项目与意图锚点

这里建议吸收你之前“原点系统”里非常有效的一层：

- 在一切故事开发之前，先建立“意图锚点”
- 后续生成、评审、改稿都默认服从这层锚点

第一版建议的锚点字段：

- 故事核
- 核心主题
- 主人公
- 情感弧光
- 核心视觉母题
- 类型 / 风格

用户输入：

- 一句话点子
- 类型
- 想做出的情绪体验
- 作品形式
- 已知意图锚点

系统输出：

- logline 初稿
- 主题问题初稿
- 最小开发骨架
- 意图锚点草案

### 步骤 2：建立故事圣经

用户补充：

- 主角和关键角色
- 主要关系
- 世界规则
- 时间线起点
- 已知伏笔

系统输出：

- 角色网
- 世界事实库
- 时间线视图
- 待补全项提醒

### 步骤 3：生成剧情大纲

系统根据故事圣经生成：

- 三幕大纲
- beats 视图
- 关键转折点
- 风险提示

### 步骤 4：拆成场景卡

每场至少要有：

- POV 角色
- 场景目标
- 阻力
- 转折
- 信息增量
- 与上下场的因果关系

### 步骤 5：运行规则检查

系统检查：

- 角色一致性
- 时间线冲突
- 世界规则冲突
- 伏笔回收缺口
- 场景目标与转折缺失
- 中段疲软
- 对白解释过载
- 制作风险热点

### 步骤 6：进入改稿循环

用户不是从空白页重写，而是从“问题清单”开始改。

系统输出的每条反馈都应该包含：

1. 问题是什么
2. 为什么它削弱观感
3. 它影响了哪些角色或场景
4. 最值得先改哪里

## 6. 第一版页面与模块

| 页面 | 主要作用 | 必须有的内容 |
| --- | --- | --- |
| 项目首页 | 看清项目状态 | logline、主题、当前版本、待处理问题数 |
| 意图锚点 | 锁定唯一真相 | 故事核、主题、主角、弧光、母题、类型、锚点变更记录 |
| 故事圣经 | 管住长期事实 | 人物、关系、世界规则、时间线、伏笔 |
| 角色网络 | 看角色张力 | 欲望、需求、缺陷、关系冲突、弧线 |
| 大纲工作台 | 组织整体结构 | 三幕视图、beats 视图、转折点、支线 |
| 场景室 | 逐场开发 | 场景卡、顺序、因果关系、情绪变化 |
| 评审中心 | 集中处理问题 | 硬性错误、质量建议、创意提示 |
| 改稿记录 | 保留决策历史 | 版本对比、接受/忽略原因、回滚点 |
| 专家面板 | 定向求助而非泛生成 | 结构天才、场景工坊、对白医生、潜台词专家、视觉锤、情感共鸣、节奏调控师、角色心理学家、一致性监察 |

## 7. 从“原点系统”吸收的机制

你提供的 V2.0 参考稿里，有四个特别值得直接吸收。

### 机制 1：意图锚点先于生成

这点和我们现在的路线完全一致，而且值得做得更明确：

- 系统先问清“想写什么”
- 再决定“怎么帮你写”

这能明显减少模型在长对话中跑偏。

### 机制 2：专家顾问团，而不是一个万能助手

这个思路非常适合产品化。

建议第一版在界面上保留“专家面板”概念，但不是让用户复制大段提示词，而是做成系统内置的调用模式。

第一批建议保留这些角色：

- 故事核挖掘者
- 结构天才
- 场景工坊
- 对白医生
- 潜台词专家
- 视觉锤
- 情感共鸣
- 节奏调控师
- 角色心理学家
- 一致性监察

### 机制 3：默认顾问模式，避免失控代写

参考稿里“AI 提供可决策选项，而不是直接替你写完”的原则很重要。

对第一版来说，这应该被正式写成默认交互规则：

- 默认给 2 到 3 个受约束方案
- 默认解释方案为什么符合当前锚点
- 用户明确要求时，才做整合稿或扩写

### 机制 4：沙盒模式

这个机制也值得保留，但应降级为可选能力，而不是默认状态。

建议产品里表现为：

- 默认是“受约束模式”
- 用户可临时切到“发散模式”
- 发散结束后，系统自动回到当前锚点并重新校验

## 8. MVP 范围

### 必须有

- 项目创建
- 故事圣经编辑
- 角色与关系管理
- 时间线管理
- 剧情大纲编辑
- 场景卡编辑
- 规则检查
- 改稿反馈与版本记录

### 第二阶段再做

- 剧本标准排版导出
- 团队实时协作
- 演员朗读模拟
- 制作预算估算
- 投稿格式细分

### 这一版先不做

- 一键生成完整长片剧本
- 大规模多人协作权限系统
- 复杂项目管理功能
- 精细化制片排期

## 9. 第一版验收标准

只要满足下面这些，这一版就算站住了：

1. 用户能在 30 分钟内从一句话点子走到第一版故事圣经。
2. 用户能在 1 小时内形成可读的大纲和场景卡骨架。
3. 系统能稳定指出时间线、知识状态、世界规则这三类明显冲突。
4. 系统能把伏笔和回收建立成可追踪关系。
5. 每个场景都能被系统要求补齐目标、阻力和转折。
6. 反馈结果能被用户逐条接受、忽略或改后复查。
7. 用户能看见“问题减少了多少”，而不是只看见新文本。
8. 用户能在“受约束模式”和“发散模式”之间切换，但系统仍记得当前锚点。
9. 用户能直接调用专家面板，而不是靠记忆复杂提示词。

## 10. 产品风险与规避办法

### 风险 1：一开始就太自由，结果数据空洞

规避方式：

- 用引导表单而不是空白文本框
- 先收最关键字段，再允许自由扩写

### 风险 2：规则检查太抽象，像在说空话

规避方式：

- 每条问题必须绑定证据对象
- 明确指出涉及的角色、场景和前后事实

### 风险 3：误报太多，用户不再相信系统

规避方式：

- 把硬性错误和软性建议分开
- 所有规则都允许“忽略并记录原因”

### 风险 4：过早做成万能平台，复杂度爆炸

规避方式：

- 第一版只服务故事开发，不吃掉全部影视生产流程

### 风险 5：角色面板做成噱头，结果没有真实差异

规避方式：

- 每个专家都绑定固定输入、固定输出和固定约束
- 不允许不同专家只是换名字说同样的话

## 11. 最稳的开发顺序

### 里程碑 1：意图锚点 + 故事圣经

先把这些能力做稳：

- 意图锚点
- 项目对象
- 角色对象
- 关系对象
- 世界规则对象
- 时间线对象
- 伏笔对象

### 里程碑 2：大纲与场景卡

在故事圣经稳定后，再做：

- 三幕大纲
- beat 列表
- 场景卡
- 场景顺序与因果链

### 里程碑 3：规则引擎 + 一致性监察

优先做最值钱的 8 个检查器：

1. 角色一致性
2. 时间线冲突
3. 世界规则冲突
4. 伏笔回收缺口
5. 场景目标缺失
6. 场景转折缺失
7. 中段疲软
8. 对白解释过载

同时补两类追踪：

- 情感弧光追踪
- 视觉母题追踪

### 里程碑 4：专家面板与改稿中心

最后补齐：

- 专家路由
- 问题列表
- 严重级别
- 版本比较
- 决策记录

## 12. 对设计和开发最重要的原则

1. 任何长程事实都不要只存在聊天记录里。
2. 任何“建议”都应尽量落到角色、场景或规则对象上。
3. 任何“生成”都应该建立在已有结构化事实之上。
4. 任何“评审”都要给证据，不要只给抽象判断。
5. 任何“专家模式”都必须有清晰边界，不能只是包装名称。
