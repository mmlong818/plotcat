# 剧情板重构方案

## 1. 目标

当前剧情板已经能做三件事：

- 剧情卡挂在幕和节点下
- 卡片可拖动到节点
- 卡片可以锁定并生成场景

但它还不够支持真正的创作排演，因为它缺少：

- 主线与支线的明确轨道
- 多方案并排比较
- 未定义内容的临时存放区
- 在“结构视图”和“排演视图”之间切换

这次重构的目标不是做自由白板，而是做“有结构约束的可拖动剧情板”。

## 2. 关键结论

### 2.1 永远只有一条正式主线

系统里可以存在多个“主线级方案”，但只有一条可以进入正式版本。

因此产品文案不建议叫“多条主线”，而建议叫：

- 正式主线
- 支线
- 未定义
- 方案轨

### 2.2 幕结构不废弃

剧情板不是替代“幕 -> 节点”，而是叠加在它之上。

也就是说，剧情板仍然属于：

- 幕
- 节点

但用户在排序和推演时，还要能看到：

- 它在哪条叙事轨道

### 2.3 卡片保持中性，区域承担归属

剧情卡不承担大面积颜色归属。

真正承担归属表达的是：

- 幕区
- 节点区
- 轨道区
- 方案区

## 3. 核心对象

## 3.1 幕

幕仍然是结构层最大单位。

作用：

- 控制整体节奏
- 控制节点分布
- 提供剧情卡的结构归属

## 3.2 节点

节点是幕下的结构挂点。

作用：

- 对齐节拍或必要桥段
- 作为剧情卡的结构锚点

## 3.3 轨道

轨道是剧情排演的横向组织单位。

建议类型：

- `canonical_mainline`：正式主线
- `subplot`：支线
- `undefined`：未定义
- `scenario`：方案轨

## 3.4 方案组

方案组用来承载“同一个问题的多个解法”。

例如：

- 主角是否牺牲
- 结局是否公开真相
- 对手是否洗白

同一个方案组下，可以有多条方案轨。

## 3.5 剧情卡

剧情卡仍然是创作期主对象。

它不只知道自己属于哪个幕和节点，还要知道：

- 自己在哪条轨道
- 自己是不是正式版本的一部分
- 自己属于哪个方案问题

## 4. 两种视图

## 4.1 结构视图

结构视图用于回答：

- 每一幕是否成立
- 节点覆盖是否完整
- 主线和支线在每一幕的密度如何

展示逻辑：

- 横向按幕
- 幕内按节点
- 节点内按轨道分行
- 每一幕是一个色块区域

在这个视图里，重点是：

- 幕
- 节点
- 结构覆盖

轨道只是一种组织方式，不抢主角。

## 4.2 排演视图

排演视图用于回答：

- 正式主线现在怎么走
- 支线如何插入
- 方案 A / B / C 哪个更顺
- 哪些内容暂时还没归类

展示逻辑：

- 横向按幕轻分隔
- 纵向按轨道
- 轨道本身是有底色的长条区域
- 卡片可在轨道内排序，也可跨轨道移动

在这个视图里，重点是：

- 轨道
- 顺序
- 方案比较

## 5. 轨道体系

推荐第一版固定这些轨道：

### 正式轨道

- 正式主线：唯一一条
- 支线 A
- 支线 B
- 未定义

### 方案轨道

- 方案轨 A
- 方案轨 B
- 方案轨 C

后续可以允许用户新增更多支线和方案轨，但第一版先固定，降低复杂度。

## 6. 数据模型变更

## 6.1 新增 `lanes`

在 `plot_board` 下新增：

```json
{
  "lanes": []
}
```

单条轨道建议字段：

- `id`
- `title`
- `kind`
- `sort_order`
- `color_slot`
- `is_canonical`
- `scenario_group_id`
- `notes`

### `kind` 枚举

- `canonical_mainline`
- `subplot`
- `undefined`
- `scenario`

## 6.2 新增 `scenario_groups`

在 `plot_board` 下新增：

```json
{
  "scenario_groups": []
}
```

单个方案组建议字段：

- `id`
- `title`
- `question`
- `status`
- `promoted_lane_id`
- `notes`

### `status` 枚举

- `exploring`
- `comparing`
- `decided`
- `archived`

## 6.3 扩充 `cards`

剧情卡建议新增这些字段：

- `lane_id`
- `lane_kind`
- `order_index`
- `scenario_group_id`
- `is_canonical`

保留现有结构字段：

- `act_id`
- `node_id`
- `type`
- `status`

这里有一个重要区分：

- `lane_kind` 表示它属于哪种叙事轨道
- `type` 表示这张卡在叙事功能上是主线、强化还是备选

二者不能混为一个字段。

## 6.4 建议的数据结构

```json
{
  "plot_board": {
    "view_mode": "structure",
    "lanes": [],
    "scenario_groups": [],
    "cards": []
  }
}
```

## 7. 交互规则

## 7.1 轨道内拖动

在同一轨道内拖动，改变：

- `order_index`

不改变：

- `act_id`
- `node_id`
- `lane_id`

## 7.2 跨轨道拖动

跨轨道拖动，改变：

- `lane_id`
- `lane_kind`
- `order_index`

如果拖入方案轨，还应补：

- `scenario_group_id`

## 7.3 跨幕拖动

跨幕拖动时，改变：

- `act_id`
- `node_id`

如果目标区域没有明确节点，优先落到该幕默认节点。

## 7.4 从正式轨复制到方案轨

这个动作不应该是“移动”，而应该是“复制一张变体卡”。

这样才能保留正式版本不被误改。

建议动作名：

- 复制到方案轨

## 7.5 从方案轨提升为正式版本

这个动作不应该直接替换所有卡，而要进入“比对确认”。

流程：

1. 选择一条方案轨
2. 查看与正式轨差异
3. 决定整体替换或局部吸收
4. 再更新 `is_canonical`

## 8. 锁定规则

锁定层不能把所有轨道都当正式事实。

只有这些内容允许投影到锁定层：

- `is_canonical = true` 的剧情卡
- 正式主线上的剧情卡
- 被明确采纳的支线卡

方案轨和未定义轨默认不投影。

## 9. 场景生成规则

场景页只从正式版本生成。

默认来源：

- 正式主线
- 已采纳支线

可选来源：

- 被用户手动指定进入拆场的方案卡

## 10. 第一版页面结构

剧情板第一页先只做两种模式：

- 结构视图
- 排演视图

并共享同一批卡片和同一份数据。

不要做三套不同的剧情页。

## 11. 迁移策略

当前系统已有：

- `act_id`
- `node_id`
- `type`
- `status`

迁移时建议这样映射：

### 默认轨道

- `type = mainline` -> `正式主线`
- `type = enhancement` -> `支线 A`
- `type = alternate` -> `未定义`

### 默认方案组

旧数据先不自动生成方案组。

只有用户明确把卡拖入方案轨后，才创建方案组或绑定现有方案组。

## 12. 第一版不做什么

为了避免重构过大，第一版不做：

- 自由画布
- 任意二维摆放
- 卡片旋转、缩放
- 无限多轨道
- 每张卡独立颜色系统

第一版重点只做：

- 轨道
- 拖动排序
- 方案并排
- 正式版本筛选

## 13. 推荐实施顺序

### 第一阶段

- 加 `lanes`
- 加 `scenario_groups`
- 给卡片补 `lane_id`
- 做结构视图

### 第二阶段

- 做排演视图
- 做轨道内排序
- 做跨轨道拖动

### 第三阶段

- 做方案轨复制
- 做方案轨提升
- 做与锁定层、场景页的联动
